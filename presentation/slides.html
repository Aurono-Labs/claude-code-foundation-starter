How I code with Claude Code 02 / 15
Problem

Long projects drift.

Aurono Labs

A weekend hack survives without structure. A real product doesn't. Across hundreds of sessions you lose coherence: vocabulary, scope, design choices, what "done" means.

Vocabulary
"Trade" ≠ "Order" ≠ "Fill"
Two engineers using the same word for different things is where rot begins.
Scope
Phase 2 leaks into Phase 1
Without a roadmap, every shiny idea looks like the next sprint.
Quality
"Done" without tests
Without a workflow, commits land at 11pm with no functional verification.

The fix isn't a smarter model. It's a written foundation the model re-anchors on every session.

Layer 3

The locked language.

Aurono Labs
→docs/domain_terminology.md →docs/non_goals.md

The rule

Terms are write-once. Never renamed. Never overloaded. If a new concept appears, you introduce a new term.

Words are infrastructure.

  • Decision ≠ Intent ≠ Trade ≠ Order ≠ Fill
  • Reservation ≠ Allocation. The non-goals file lists what we explicitly will not do.
  • The cost: 20 minutes once. The payoff: weeks of avoided ambiguity in code, events, UI, docs.
From Aurono Start → docs/domain_terminology.md — § Forbidden Substitutions
allocation≠reservation execution ≠decision order ≠trade intent ≠decision trade ≠round trip
"If you feel the urge to reuse a term for a new meaning, you need a new term instead." — v1.0, locked.

→docs/design/design_system.md →docs/design/user_journeys.md →docs/testing/test_suite.md →docs/functional_tests.md

The senses, and the proof.

  • Design system: colors, typography, accessibility floor (WCAG 2.1 AA). One register per surface.
  • User journeys: who does what, when. Features map to journeys, not the other way around.
  • Test suite: every test file documented — what it covers, why it exists.
  • Functional tests: open → passed/failed. A Phase 4 deliverable, not an afterthought.

The Method

For each layer: have a conversation.

Aurono Labs

Don't drop these files in the repo and hope. For each one, work it through with Claude Code until the doc is strong enough to push back on bad ideas.

1

Read it together

"Read vision_and_mission.md. Tell me what you think it commits us to."

2

Stress-test it

Propose a bad idea. Watch it push back. If it doesn't, the doc isn't strong enough — fix the doc.

3

Lock it

Add a sentence to CLAUDE.md: "all work must align with X, defined in <file>."

4

Move to the next layer

Vision → Roadmap → Terminology → Plan → Design → Tests → Workflow.

Total cost: roughly two hours of focused conversation per project. Payback: within the first week.

The Workflow

Six phases, five triggers.

Aurono Labs

Once the foundation is in place, daily work becomes almost mechanical. Each trigger is a short phrase the operator types; the model knows what to do next.

PHASE 1
Idea Intake
"New idea: …"
PHASE 2
Backlog or Park
"Add to backlog"
PHASE 3
Planning
"Let's build X"
PHASE 4
Execution
"Plan accepted"
PHASE 5
Functional Testing
(operator tests)
PHASE 6
Closing
"FTs closed"

No drift. No "wait, what were we building again?" No commits to master at 11pm with no tests.
